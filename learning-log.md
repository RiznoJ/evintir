## August 11 — China Strategic Reference Layer, built in two phases
- What I did: Biggest single feature to date, split into two phases on purpose instead of one big drop. Phase 1 built the skeleton — a new opt-in map layer of 14 fixed public-source Chinese strategic sites (CMC, theater commands, fleet HQs, the Rocket Force, and the post-April-2024 ASF/CSF/ISF split), reachable from China's existing country popup without touching its News/Analyst tabs. Phase 2 came back the same day and substantially deepened it — expanded the dataset to 31 sites, added a Major/All tier toggle, category filters, a live context summary, a text search, and attribution to the outside researcher whose public map inspired the feature. This entry leans harder than usual into the actual computer-science mechanics — how the data gets pulled, and the different layers of comparison I had Claude Code run to catch problems — since that's the part I want documented properly this time, not just the feature list.
- The pulling — how and when data actually gets fetched:
  - The 14/31-site file is fetched with the browser's `fetch()` API, which is asynchronous — the page doesn't freeze waiting on the network, and the calling code has to `await` the response and explicitly check `res.ok` before trusting it, exactly like the existing events/notes/risk-history loaders on the map page already do (I directed Claude Code to match that existing pattern instead of inventing a new one).
  - Lazy pull, not eager: the fetch only fires the first time a visitor actually opens the strategic view, not on page load — and the result is cached in memory after that first successful pull, so opening/closing the view repeatedly never re-hits the network. A failed pull sets a "don't retry" flag instead of hammering a broken URL every time someone clicks in.
  - Every marker's "View area on Wen's map" link is also a small pull-adjacent operation: instead of fetching anything from his map, it's a URL built purely from that site's own already-loaded coordinates (lat/lng substituted into a template string), so it can never leak or depend on his live map being reachable — Evintir never pulls from his map at all, only links out to it.
- The comparing — every point where I had Claude Code check computed output against an expected value, not just eyeball it:
  - Schema comparison: instead of manually scanning 31 JSON objects for a typo'd or missing field, wrote a Python check that pulls the property-key set off every single feature and compares it against the fixed 12-key schema set using symmetric difference (`keys ^ schema`) — any feature whose keys don't match exactly gets flagged by name automatically. Zero mismatches, confirmed programmatically, not by reading.
  - Count comparison: after building the category/tier filters, cross-checked the UI's own live summary numbers against an independent Python tally of the same raw file (grouping features into dictionaries by category, importance, and verification_status and counting each bucket) — the browser-rendered "Navy 6 · Air 1 · Ground 0 · Rocket 8..." line had to match the independently-computed dictionary counts exactly, and toggling the Rocket checkbox off had to drop the total by precisely 8, not roughly 8. That's a real regression test, not a glance at the screen.
  - Content comparison against the brief itself: the task described "28 core sites plus a separate 4-site block, 32 total," but only one JSON block was actually provided. Counted the IDs in that block programmatically (31, no duplicates) instead of assuming the prose description was right, and flagged the mismatch rather than quietly inventing a 32nd site to make the numbers line up.
  - Regex comparison for stale terminology: grepped every site's description text for "Strategic Support Force" (a Chinese military organization dissolved in April 2024) to make sure none of the entries had reintroduced it as a still-active body — the two hits that came back were both clearly historical/lineage phrasing ("formerly," "passed through... to today's"), not a live reference, so nothing needed correcting.
  - Security-relevant comparisons: every source URL (both the site's own citation link and the constructed Wen-map link) gets run through a regex check (`/^https?:\/\//i`) before it's ever allowed to render as a clickable link — a comparison against an allowlist pattern, not a blocklist — and every piece of text that came from the data file gets passed through an HTML-escaping function before insertion into the page, so a malicious or malformed string in the data can't execute as markup. Same discipline the rest of the site already uses for RSS-sourced text; extended it here rather than treating "our own static file" as automatically safe.
  - Before/after comparison as the actual debugging method, twice: the first real bug (exiting the strategic view right after using search left the map stranded instead of resetting home) was found and fixed by literally capturing the map's raw center coordinates and zoom level via the browser's JavaScript context immediately after clicking Exit, comparing those actual numbers against the expected target (`[25, 30]`, zoom 2), seeing they didn't match, forming a hypothesis (a Leaflet zoom animation from the search jump was still in flight and racing the reset), changing the code, then re-running the identical capture-and-compare to confirm the numbers matched exactly afterward — not "looks fixed," a real before-value vs. after-value diff. The second bug (Phase 2's taller panel pushing the Exit button below the visible scroll area on a 390px mobile screen) was found the same way: captured the button's actual on-screen bounding-box coordinates via the browser, compared them against the panel's own visible box, saw the button's position fell well outside it, fixed the CSS, then re-captured and re-compared to confirm the button's box now sat inside the panel's visible bounds.
- What broke / caught in verification: Both Leaflet bugs above were invisible from reading the code — the animation race and the mobile scroll-clipping both only showed up once real coordinates/bounding boxes were pulled from an actual running browser and compared against what was expected, not reasoned about from the CSS and JS in the abstract. Also re-ran the original Phase 1 hard constraint — rename the data file, confirm the layer fails non-fatally and the rest of the site is unaffected — a second time after Phase 2 tripled the dataset and added a much bigger UI, since a constraint that held once doesn't automatically still hold after a feature grows.
- What I learned (plain English): Today's real lesson was that "verification" isn't one thing — it's several different kinds of comparison stacked on top of each other: comparing a data file's structure against a fixed schema, comparing a UI's live output against an independently-computed expected value, comparing a stated feature count against what was actually provided, and comparing a program's raw internal state before and after a fix to prove a bug was real and the fix actually closed the gap, not just to eyeball a screenshot and assume it looked right. None of those are the same check, and skipping any one of them would have let a real bug or a real data mismatch through.
- Roadmap / next steps: two open judgment calls sitting with me, not resolved silently — whether the 31-vs-32 site count needs a real 32nd entry, and whether "Central/Political-Military" should split into two separate checkboxes instead of the one combined checkbox I built. Search is intentionally a simple substring match capped at 8 results, not a real search engine. Two of the eight category values (Ground, Political-Military) already have working filters and marker colors with zero matching sites yet — ready to receive real sourced entries whenever I have them, nothing left to build.

## August 20–21 — Tech Watch: building an automated video-index pipeline (and debugging it the hard way)
Added a third tab to Evintir: Tech Watch, a filterable index of defense-technology developments pulled from three YouTube channels (Sandboxx, Cappy Army, DARPAtv), covering the war's start on 28 February 2026 forward. This is deliberately a collection layer, not an analysis layer — each entry is a short descriptive blurb about what a set of source videos covers, with links out, not an assessment. The disclosure banner and the visual separation from Analyst Notes are there to keep that distinction honest: Tech Watch tells a reader what's out there to watch; Analyst Notes is where I make sourced, confidence-labeled claims in my own voice.

**The design**
The unit of the feed is a development, not a video — when several channels cover the same thing, that's one entry with multiple source links, so ~150 indexed videos collapse to a few dozen clusters. The pipeline splits into two halves for a real technical reason: detection runs in GitHub Actions (RSS polling every 6 hours, standard-library Python only, no dependencies) because YouTube blocks datacenter IPs for anything heavier; extraction (yt-dlp, transcripts, the blurb-drafting API calls) runs locally on my machine. Blurbs are drafted by a scripted Haiku loop under a strict prompt — describe what the video covers, never assert facts about the world, no invented figures — and nothing publishes without me approving the cluster first.

**What broke, and what it actually took to fix it**
This is the part I want to remember, because the design was fine and the execution was rough for most of two days.

First real failure: a 3h45m run that produced nothing. The original index_channels.py walked a channel's entire upload history and applied the 28 Feb floor date as a post-fetch filter instead of a stop condition — so it enumerated years of back catalog just to discard almost all of it. It had no incremental checkpointing, so everything sat in memory until a final save that never came. I let it run for hours with zero visibility, checking in periodically and getting nothing back but "still working." Eventually killed it and made Claude Code prove, with real command output, that the process was actually alive rather than stuck — ps -p <pid>, not vibes — before deciding what to do next.

Second failure, hiding under the first: the android-client bug. Once I forced real logging, it became clear the slow path wasn't just "big catalog" — roughly 94% of the per-video date lookups were failing outright. The cause was which yt-dlp extraction path a video took: the fallback lookup forced yt-dlp's default "web" client, which YouTube has been actively rejecting with "The page needs to be reloaded." One flag fixed it — --extractor-args "youtube:player_client=android" — the exact workaround my own fetch_transcript.sh already used elsewhere in the repo. Confirmed by hand on a single video before touching any code: same call, one flag, dead vs. resolved.

The fix that actually mattered: bound the worst case instead of hoping. Rather than just re-running the same open-ended scan and hoping it behaved, I had it cap the listing (--playlist-end 150), stop after 5 consecutive pre-floor videos, checkpoint every 20 videos, and log unbuffered so I could tail -f a real file and watch actual progress instead of trusting a chat window's "still thinking" animation. That change alone turned an unknown, unbounded, multi-hour black box into something I could watch tick forward in real time.

A process bug I caught before it published. The transcript-fetch step wasn't restricted to approved clusters — it also considered drafts — so its first pass spent budget on 4 unapproved clusters, leaving 4 real approved ones with no blurb. Caught it by asking for exact numbers before letting anything publish, not by trusting a summary.

The dumbest, most recurring failure of the whole two days. The local python3 -m http.server kept dying — killed by a stray port-clearing command, or just left behind from an earlier session — and more than once I mistook a dead server for a broken pipeline. Wasted real time debugging data that was fine, served by nothing.

What this actually cost, honestly. This wasn't a quick pipeline run. I left my laptop open and plugged in overnight, twice, with display-sleep pushed out to hours so a background process wouldn't die mid-run. I checked in from my phone at the gym. I watched a live log stream from the airport before boarding. None of that was necessary in principle — a correctly-bounded script should run in minutes — but the first version wasn't bounded, and I only found that out by watching it fail slowly instead of failing fast. Next time: force real logging and a hard runtime cap on anything that touches an external API or scrapes at scale, before the first real run, not after three hours of silence.

**Final state**
150 videos indexed (Sandboxx 60, Cappy Army 56, DARPAtv 34); 5 landed in a needs_date quarantine bucket (deleted/private/members-only — no normal metadata) and are correctly excluded from clustering rather than corrupting it. 66 relevant videos, 30 clusters, top clusters approved and published with drafted blurbs. Detection now runs on its own every 6 hours; publishing stays a manual, reviewed step by design.

**Judgment calls worth remembering**
- Bound the scan, don't let it run open-ended. The original "index everything since February" instinct assumed a video count nobody had actually checked. Capping worst-case runtime is worth a small loss of completeness.
- Keep the pipeline non-generative where it matters. Detection, clustering, and date resolution are all deterministic code, not model calls — the only place a model touches the output is the descriptive blurb, and even that gets a human approval gate before it goes live.
- Test before scaling, and never trust a UI's silence. Both bugs were invisible until I forced real logging and checked a single case by hand. A loading animation is not a status report; a log file you can tail -f is.
- When something silently runs for hours, stop and demand proof, don't just wait longer. "Still working" from a chat panel isn't evidence. ps -p <pid> and a real log file are. I should reach for that the first hour, not the fourth.

**Loose ends**
- 22 clusters remain in draft for a future approval pass.
- One cluster has no captions on either candidate video and needs a hand-written blurb if I want it live.

## August 25 — Catch-up extraction: closing a four-day detection/extraction gap, end to end
Detection (`watch_channels.py`) has been running on its own in GitHub Actions every 6 hours since the 20th, exactly as designed. Extraction never has a schedule, on purpose — it needs yt-dlp against a residential IP, which means it only runs when I sit down and run it by hand. Nobody had since the 21st, so four days of RSS hits just sat in `data/watchlist.json` at `status: "indexed"`, detected but never clustered or transcribed. Not a bug, just the tradeoff of a local-only extraction half — worth writing down so a multi-day gap like this doesn't look alarming next time it happens.

**Finding the actual backlog**
Asked for everything indexed since the 19th; the real number was bigger. My local `data/watchlist.json` was stale (last touched the 21st), so the CI-committed refreshes from the 21st through today hadn't been pulled in yet — a fast-forward `git pull` was clean since nothing local had touched that file. Once current, the indexed-but-unprocessed count was 18, not 7: the 7 from the 19th on, plus 11 older ones from Aug 8–18 (three days of DARPA Lift Challenge broadcasts, three Sandboxx fighter-aircraft breakdowns, one Cappy Army video) that had also never made it through a clustering pass. Flagged the discrepancy and got confirmation to process all 18 in one run rather than silently narrowing scope to the number I'd originally asked about.

**Running it**
`build_clusters.py` classified 10 of the 18 as relevant (8 hit exclude-keyword or no-topic-match filters) and formed 3 new draft clusters — one DARPA Lift Challenge cluster (7 videos), one Navy fighter-aircraft cluster (2 videos), one Cuba/Iran-drone cluster (1 video). `fetch_representatives.py` and `draft_blurbs.py` ran scoped to just those 3 cluster IDs, on purpose — the same eligibility check also surfaced 7 pre-existing draft clusters from March through July that were sitting unblurbed for unrelated reasons, and pulling those into today's run would have quietly expanded a detection-gap catch-up into a second, different backlog. Left them alone.

**A fourth video, added by hand**
One of the 8 filtered out as "irrelevant" — an AIM-424 air-to-air missile video from Sandboxx — got a manual override after a second look: the keyword filter has no "air-to-air missile" bucket in its closed topic vocabulary, so it fell through, but it was clearly in scope. Ran it through the same transcript/blurb steps by hand, outside `build_clusters.py`'s classifier, and gave it its own cluster (`Hypersonics & Long-Range Strike`) since it didn't fit the topic of any of the other three.

**Local preview caught a stale server before it caused confusion**
The local preview server was still running from a previous session — but serving from `~/Desktop`, not the repo, a repeat of the exact "dead server mistaken for a broken pipeline" failure mode from the 20th–21st build. Killed it and started a fresh one rooted correctly before doing any review.

**How this actually got published**
Reviewed all 4 clusters on localhost and got the go-ahead to push. Publishing here didn't go through `publish_techwatch.py` — that script only reads clusters at `status: "approved"`, and these were still `status: "draft"`. Instead of hand-setting `approved` and then running the normal script, I wrote a one-off merge (same item-building logic as `publish_techwatch.py`, applied to just these 4 cluster IDs) straight into `data/techwatch.json`, then deleted the 4 clusters out of `data/clusters_draft.json` once they were confirmed live. Functionally the same gate — nothing published without me looking at it on localhost and saying so explicitly — but worth being honest that the mechanism was custom, not the documented `draft → approved → publish` path. If this pattern repeats, it's worth either scripting the "approve + merge + prune" sequence properly or just using the real approve field and running `publish_techwatch.py` as designed.

**Final state**
4 clusters / 11 videos live in `data/techwatch.json` on `main` (pushed as `f1e5ef4`), real publish dates preserved throughout (Aug 8, 11, 21, 24 — never today's date). `data/clusters_draft.json` has the 4 published clusters removed and the 7 unrelated older drafts plus everything else untouched. `data/watchlist.json`'s status transitions from this run (clustered/transcribed/irrelevant) got committed alongside rather than left stale for next time. Working tree clean, local preview server stopped.

**Judgment calls worth remembering**
- A stale local file can make a backlog look smaller than it is. Always pull before counting anything CI might have touched since the last local session.
- When a scoped ask turns out to undercount the real backlog, say so and ask, rather than either quietly expanding scope or quietly dropping the extra items.
- "Eligible for this script" and "in scope for this task" aren't the same set. `fetch_representatives.py`/`draft_blurbs.py` will happily pick up any unblurbed draft cluster, old or new — scoping by `--cluster-id` to just the ones this run created kept an unrelated older backlog from riding along.
- A closed keyword vocabulary will always miss some in-scope items at the edges (the AIM-424 video). That's the right failure mode for a filter — quietly wrong would be worse than visibly incomplete and correctable by hand.
- Leaving state uncommitted "to stay scoped" can just relocate the staleness problem to next session. Committing `watchlist.json`'s real status transitions alongside the publish was worth the slightly wider diff.

**Loose ends**
- 7 older draft clusters (March–July) are still sitting unblurbed, for reasons unrelated to this run — a separate cleanup pass, not today's problem.
- `sources/fetch_transcript.sh` has never been committed on any branch, repo-wide — the pipeline depends on it but a fresh clone wouldn't have it. Noticed while checking git status before this push; not today's task, flagging for a deliberate decision later.
- Today's publish used a one-off merge script instead of the documented `approved` → `publish_techwatch.py` path (see above) — fine for a single catch-up, but if this becomes routine it should get formalized instead of repeated ad hoc.
- Extra drafted-but-unpublished blurbs from the mis-targeted run are a cheap head start whenever I approve more.
